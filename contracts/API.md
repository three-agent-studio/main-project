# API и правила расширения

Владелец общих контрактов — участник №1. Изменения согласуются с потребителями №2/№3.
OpenAPI генерируется из DRF serializers/views командой `python manage.py spectacular --file ../contracts/openapi.generated.yaml --validate --fail-on-warn`.
Схема contracts/openapi.generated.yaml сохранена в репозитории; CI генерирует её повторно и проверяет отсутствие расхождений. Изменять её только генератором.

## Реализованный фундамент

| Метод | Адрес | Доступ и ответ |
|---|---|---|
| GET | `/health/live/` | Публичный, `{"status":"ok"}` |
| GET | `/health/ready/` | Проверка БД; 200 или 503, без деталей подключения |
| GET | `/api/v1/csrf/` | `{"csrfToken":"…"}` и CSRF cookie; не сохранять в localStorage |
| GET | `/api/v1/me/` | Только сессия; id, username, roles, student_profile и staff_profile (объект или null) |
| GET/POST | `/auth/login/` | Django LoginView, HTML-форма и CSRF; после входа `/profile` |
| POST | `/auth/logout/` | CSRF обязателен, сессия удаляется, redirect на `/auth/login/` |
| GET | `/api/v1/schema/` | Только административный пользователь |

`student_profile`: full_name, faculty, programme, course, group. Профиль доступен только для чтения.
`is_staff` означает доступ к Django Admin, **не роль сотрудника деканата**. Роль деканата задаётся только явным `StaffProfile`, который привязан к одному факультету. Его назначает/изменяет/удаляет superuser через Django Admin.

`roles` — список бизнес-ролей: `student` при наличии StudentProfile и `deanery_staff` при наличии StaffProfile. Оба профиля могут быть назначены явно (например, сотрудник также учится), но области доступа к личным и служебным данным не объединяются. Один технический флаг is_superuser сам по себе не открывает служебные API.

`staff_profile`: full_name, faculty (название), faculty_id. `/me/` возвращает только профили самого вошедшего пользователя и не принимает POST/PUT/PATCH/DELETE. API не позволяет менять себе факультет, группу, владельца, пароль или роли.

## Общие соглашения

- Только JSON для `/api/v1/`; аутентификация — серверная сессия, 403 при отсутствии сессии.
- Ошибки DRF: `{ "error": { "status": 403, "details": { "detail": "…" } } }`.
  Не-API маршруты (CSRF middleware, HTML login, 404 URL) могут вернуть HTML: клиент учитывает Content-Type.
- Списки: `{count, next, previous, results}`; по умолчанию 25 записей на страницу.
- Время — ISO 8601 с часовым поясом, хранение UTC, показ в часовом поясе вуза.
- Владелец определяется по request.user. UUID/скрытый UI не заменяют авторизацию.
- List/detail/update/delete фильтруются по области доступа; чужой объект — 404.
- Cookie/CSRF передаются только в пределах своего origin. POST/PATCH/DELETE требуют X-CSRFToken.
- Клиент не назначает себе роль, группу, владельца заявки или статус.

## Расписание — первый этап #7

Реализованы `GET /api/v1/lessons/` и `GET /api/v1/lessons/{uuid}/`.
Требуется сессия и StudentProfile. Доступны только занятия текущей группы студента;
служебная роль или superuser без StudentProfile не расширяет доступ. Чужой UUID — 404,
отсутствующая сессия/студенческий профиль — 403. Изменяющие HTTP-методы не поддерживаются.

Параметры списка:
- `from`, `to`: даты `YYYY-MM-DD` включительно в диапазоне 2000–2100 годов, период от 1 до 31 дня.
- Без параметров — текущая неделя с понедельника по воскресенье в `UNIVERSITY_TIME_ZONE`.
- Только `from` — семь дней начиная с этой даты; только `to` — от понедельника текущей недели.
- Неверная дата, выход за диапазон дат (включая автоматически вычисленный конец), обратный или слишком длинный период — 400 в общем формате ошибок API.
- Учитывается пересечение интервалов: занятие, продолжающееся после полуночи, видно в обоих днях.
- Список использует **текущие** время и группу. Перенос за пределы периода виден в новом периоде;
  старое время остаётся в истории. Отменённые занятия остаются в списке с `status=cancelled`.
- `page` и общая пагинация `{count, next, previous, results}`; порядок `starts_at`, `id`.
- Переданные клиентом `group_id`, `user_id` и другие неизвестные параметры не меняют область доступа.

DTO занятия:
```json
{
  "id": "69f245e0-b301-43db-bd0b-babf1a379ea0",
  "group": "ДЕМО-1",
  "subject": "Демо: базы данных",
  "teacher": "Вымышленный преподаватель",
  "room": "ДЕМО-202",
  "kind": "practice",
  "starts_at": "2026-11-17T11:00:00+03:00",
  "ends_at": "2026-11-17T12:30:00+03:00",
  "status": "scheduled",
  "revision": 1,
  "updated_at": "2026-11-16T09:00:00+03:00",
  "last_change": null
}
```
`kind`: `lecture | seminar | practice | lab`; `status`: `scheduled | moved | cancelled`.
В примере занятие ещё не изменялось; после изменения API возвращает объект с полями
`id`, `revision`, `reason`, `before`, `after`, `created_at`. Снимки содержат
`subject`, `teacher`, `room`, `kind`, `starts_at`, `ends_at`, `status`; время в снимках
нормализовано в UTC. Внутренний `group_id` сохраняется в событии БД для уведомлений,
но исключён из студенческого DTO. При отсутствии истории `last_change=null`.
Причина изменения видна студентам группы: внутренние заметки в неё не включать.
Интерфейс показывает бейдж переноса/отмены и причину; старые значения доступны в `last_change.before`.

Занятие — отдельное событие в календаре; повторяемость и импорт расписаний не реализованы.
Применение расписания и демонстрационные данные —
[DEVELOPMENT.md](../docs/DEVELOPMENT.md#расписание--первый-этап-7).

## Защита входа и сессий — задача #5

Django LoginView и Django Admin защищены django-axes 9 с общими DB-счётчиками. После 5 неудачных попыток для нормализованного username вход временно блокируется на 15 минут; ответ 429 содержит Retry-After и страницу повторного входа. Политика действует и для неизвестных имён, не раскрывая наличие аккаунта. Успешный вход очищает прежние неудачи, запросы во время блокировки не продлевают её.

Ограничение намеренно по учётной записи, не по IP: смена сети/браузера не обходит счётчик и один пользователь не блокирует весь вуз за NAT. IP и заголовки X-Forwarded-For не используются. При необходимости глобальной защиты публичного периметра её нужно отдельно настраивать на доверенном reverse proxy.

Axes W006 рекомендует IP-счётчик; предупреждение точечно подавлено с пояснением в settings, поскольку выбран account-wide ключ. Регрессии проверяют смену IP, User-Agent, cookies и Unicode/пробелы. Axes остаётся включённым в тестах.

Сессия хранится на сервере, ключ меняется при входе; выход уничтожает сессию. Смена пароля и деактивация инвалидируют прежнюю авторизацию на следующем запросе. Не-API ответы блокировки и ответы персональных API имеют Cache-Control: private, no-store.

Операционная инструкция для администратора при необходимости досрочной разблокировки:

```sh
python manage.py axes_reset_username demo_student_a
```

## Общая граница доступа для модулей №1 и №3

Утилиты находятся в `backend/accounts/access.py`:

- `require_student(request.user)` — возвращает текущий StudentProfile или запрещает действие; применять при создании заявки/личной записи, а не принимать student_id из тела запроса.
- `scope_student_records(queryset, request.user)` — фильтрует по владельцу через FK `student` → StudentProfile. Не расширяет доступ сотрудникам или superusers.
- `scope_faculty_records(queryset, request.user)` — только факультет явно назначенного сотрудника; для чужого факультета/без назначения возвращает пустую выборку.
- `IsDeaneryStaff` — проверка права на служебный endpoint; применять вместе с фильтрацией queryset. Одна permission-проверка не фильтрует списки.

`student_path` задаётся разработчиком под связь модели, для queryset самого StudentProfile — пустая строка. Никогда не брать этот аргумент из запроса клиента. List/detail/update/delete работают с уже ограниченным queryset; тогда подмена pk приводит к 404, а не к выдаче чужих данных.

Служебный список не добавляет условие OR по владельцу: даже если сотрудник является студентом другого факультета, его личная запись доступна через личный раздел и не попадает в служебную область. Отзыв StaffProfile прекращает доступ без изменения is_staff.

## Преподаватель и успеваемость

`/me/` возвращает read-only `teacher_profile: {full_name, faculty, is_active} | null`
и роль `teacher` только для активного TeacherProfile. Роль не выдаёт `is_staff`,
`is_superuser` или права сотрудника деканата. Вход преподавателя без студенческого
профиля ведёт на `/teaching`; валидный явный `next` имеет приоритет. Двойная роль
сохраняет отдельные личную и преподавательскую области.

Назначения преподавателя (`TeachingAssignment`: группа, дисциплина, семестр) создаёт
только администратор через Django Admin. Группа и преподаватель должны относиться
к одному факультету. После создания назначение неизменяемо, кроме `is_active`;
для передачи дисциплины создаётся новое назначение. Отзыв роли или назначения
проверяется сервером заново при каждом запросе.

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/api/v1/teaching/assignments/` | Только активные собственные назначения |
| GET, POST | `/api/v1/teaching/activities/` | Собственные работы; фильтр `assignment` |
| GET, PATCH | `/api/v1/teaching/activities/{uuid}/` | Просмотр/редактирование своей работы |
| GET | `/api/v1/teaching/activities/{uuid}/students/` | Ведомость: id, full_name, result текущих студентов группы |
| GET, POST | `/api/v1/teaching/activities/{uuid}/results/` | Результаты своей работы; выставление/исправление результата |
| GET | `/api/v1/activities/` | Студент: задания, контрольные, зачёты и экзамены текущей группы |
| GET | `/api/v1/assessments/` | Студент: только личные результаты, включая прежние группы |

Все списки пагинированы. JSON-записи POST/PATCH требуют действующие сессию и CSRF.
Без роли — 403, чужая работа/студент другой группы — 404; чужое назначение в форме
создания — 400. Подмена owner/user/teacher/group не выдаёт прав. Удаление работ и
результатов через API не поддерживается: работу можно отменить, результат исправить.

Работа: `assignment` (id назначения), `kind: homework | test | credit | exam`,
`title` (до 200), `description` (до 5000), `scheduled_at`, `due_at` (ISO8601 или null),
`room` (до 100), `is_cancelled`. Для ДЗ обязателен due_at, для остальных работ —
scheduled_at. Если заданы оба времени, due_at не раньше scheduled_at. Сервер также
возвращает `id`, `subject`, `term`, `group_name`, `teacher`, `revision`, `updated_at`.
PATCH требует `expected_revision` текущей работы; назначение и вид работы неизменяемы.
Отмена не удаляет уже выставленные результаты.

Выставить результат:
```json
{"student": 12, "expected_revision": 0, "status": "graded", "score": 5, "comment": "Демо-результат"}
```
`student` — id StudentProfile из ведомости, не User. `expected_revision=0` означает
новую запись; для исправления требуется текущая revision результата. Ответ 201 при
создании, 200 при исправлении. Повтор того же решения с актуальной revision не
порождает новую историю. Устаревшая revision — 400 с предложением обновить ведомость.

Статусы: `graded` (оценка 2–5 обязательна), `passed`, `failed`, `debt` (score=null).
Результат содержит `id`, `student`, вложенную работу `activity`, `status`, `score`,
`comment` (до 2000), `revision`, `updated_at`, `is_debt`. Долг — явный debt, failed
или оценка 2. Новый успешный результат (passed или оценка 3–5) закрывает долг;
прежнее решение остаётся в AssessmentChange. Само истечение срока не создаёт долг.
У отменённой работы выставление результатов заблокировано.

Фильтры личной успеваемости: `term` (точный семестр) и `debt=true|false`; неверное
значение debt — 400. При переводе в другую группу личная история сохраняется,
но прежний преподаватель больше не видит/не меняет результаты переведённого студента.

Все изменения результатов проходят через `academics.teaching_services.set_result`:
проверка назначения и состава группы внутри транзакции, блокировка работы/студента,
валидация версии, запись результата и AssessmentChange вместе. Если история не
сохранилась, оценка тоже не изменяется. Не редактировать результаты через прямой
save/update/bulk-операции, обходящие этот сервис.
