# Разработка и расширение каркаса

## Расписание — первый этап #7

Приложение `backend/academics` принадлежит №1. Студенческий API только читает занятия
своей группы; подключение интерфейса принадлежит №2 (контракт — `contracts/API.md`).
Доступ к Django Admin доступен администраторам через локальную разработку; публичный
режим team-preview по-прежнему закрывает `/admin/`.

Перед выпуском новой версии сохранить резервную копию рабочей БД и применить миграции
с корректным окружением PostgreSQL: `python backend/manage.py migrate`.
Миграция `academics/0001_initial` добавляет таблицы, не меняя пользователей и пароли.
Миграции рабочей БД при разработке этой задачи автоматически не запускаются.

Для существующей **демонстрационной** группы можно явно добавить четыре вымышленных
занятия на текущую неделю, включая перенос и отмену:

```sh
python backend/manage.py seed_demo_schedule --group ДЕМО-1
# Для фиксированной недели (дата должна быть понедельником):
python backend/manage.py seed_demo_schedule --group ДЕМО-1 --week-start 2026-11-16
```

Повтор команды для той же группы/недели не создаёт дублей и не отменяет ручные изменения.
Команда не создаёт пользователей или группы и не меняет пароли. Не применять её к реальным
учебным данным. При смене недели добавляется отдельный набор занятий.

Все изменения существующего занятия проходят через `academics.services.change_lesson`:
блокировка строки, проверка `expected_revision`, валидация, запись занятия и LessonChange
в одной транзакции. Не использовать `QuerySet.update`, bulk-операции или прямой `save`
для редактирования расписания: они обходят историю. Admin использует сервис, требует
причину и отклоняет устаревшую форму. Группа существующего занятия не переназначается;
для другой группы создаётся отдельное событие. Занятия отменяются вместо удаления.

Для №3: `LessonChange` — сохранённое событие изменения для будущих уведомлений #9.
Оно содержит UUID, lesson_id, revision, before/after с group_id, причину и время создания.
Читать только после commit и устранять дубли по UUID события. События не редактировать
и не удалять; отметки обработки будущего потребителя хранить отдельно. Доставка
уведомлений и фоновые задачи пока не реализованы. Этот PR закрывает только расписание,
а не всю задачу #7 (в ней остаётся успеваемость).

## Языки и ответственность

Сервер — **Python 3.12+ / Django 5.2 / DRF**. Интерфейс — **TypeScript / React**, разметка JSX и CSS Modules. База — PostgreSQL 17.

- №1: `backend/config`, `backend/accounts`, `backend/core`, будущий `backend/academics`, `contracts`.
- №2: `frontend/src/app`, `frontend/src/shared`, `frontend/src/features/student`.
- №3: будущие `backend/service_requests`, `backend/notifications`, `frontend/src/features/staff`, инфраструктура и E2E.
- Общие Python-зависимости и маршруты сервера меняет №1; frontend package/lock/router — №2.
- Миграции принадлежат Django-приложению; не редактировать чужие уже применённые миграции.

План: https://github.com/three-agent-studio/main-project/issues/2. Эта основа относится к #3/#4 и частично #5.
Не добавлены фиктивные API расписания/заявок: реальные модули подключаются по мере выполнения Issues.

## Первый запуск

Требуются Python 3.12+, Node 22.13+, npm и Docker Compose (либо установленный PostgreSQL).
Из корня репозитория:

```sh
cp .env.example .env
# Заполнить POSTGRES_PASSWORD в локальном .env. Файл содержит только shell-совместимые значения.
docker compose up -d db
python3 -m venv .venv
. .venv/bin/activate
pip install -r backend/requirements-dev.txt
set -a
. ./.env
set +a
cd backend
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Во втором терминале:

```sh
cd frontend
npm ci
npm run dev
```

Открыть `http://127.0.0.1:5173`. **Все браузерные запросы через этот origin**, включая /admin и /auth: Vite проксирует их в Django.
Через `/admin/` создать только вымышленные Faculty, StudyGroup, обычных User и StudentProfile. Не выдавать студентам is_staff/is_superuser.
Для входа студента используйте `/auth/login/`; административная учётная запись без StudentProfile допустима, интерфейс показывает соответствующее состояние.
Команда create_demo_student создаёт локальных студентов; StaffProfile для обычного пользователя назначает superuser в /admin/. Кабинет обработки заявок сотрудником — #8.

## Проверки

```sh
cd backend
../.venv/bin/ruff check .
../.venv/bin/python manage.py check
../.venv/bin/python manage.py makemigrations --check --dry-run
../.venv/bin/pytest
cd ../frontend
npm run lint

```

По умолчанию pytest использует SQLite только для быстрых тестов; `TEST_POSTGRES=1` включает PostgreSQL. CI проверяет PostgreSQL, миграции, API-схему, линтеры и frontend build/tests.
Production никогда не переключается на SQLite при ошибке конфигурации.

## Как добавить раздел интерфейса

1. Создать свою папку `features/student/<feature>` или `features/staff/<feature>`.
2. Экспортировать из `index.ts` дескриптор AppModule с уникальными id/path и lazy-компонентом.
3. Подключить экспорт в `app/modules.ts`: меню и маршруты формируются из одного списка.
4. Использовать `Page`, `Card`, CSS Modules и токены `shared/styles/tokens.css`.
5. API вызывать через `shared/api/client.ts`; предусмотреть загрузку, отсутствие данных, ошибку и повтор.
6. Защищённость маршрута в UI — удобство, а не контроль доступа. Сервер обязан проверять права.

Пример публичного экспорта:

```tsx
import { lazy } from 'react';
import type { AppModule } from '../../../shared/types/module';
export const scheduleModule: AppModule = {
  id: 'schedule', path: '/schedule', label: 'Расписание',
  Component: lazy(() => import('./SchedulePage')),
};
```

Feature-модули не импортируют внутренности друг друга. Общие элементы переносить в shared только при реальном повторном использовании.
Код содержит пояснения к решениям, особенно сессиям, кешированию и расширению модулей; комментарии должны объяснять причину, а не повторять строку кода.

## Как добавить серверный модуль

Создать Django app с собственными models/serializers/views/urls/tests/migrations. Согласовать контракт и добавить app в settings, маршруты — через include.
Имя `service_requests` выбрано вместо `requests`, чтобы не затенять популярную Python HTTP-библиотеку.
Пользователь — `settings.AUTH_USER_MODEL`, не прямой импорт встроенного auth.User.
Изменение модели → новая миграция → тест на PostgreSQL. Проверять чужой доступ к спискам и отдельным объектам, а также подмену владельца при создании.

## До публичного выпуска

Каркас ещё не полный MVP. Вход защищён DB-счётчиками django-axes, роль сотрудника ограничивается StaffProfile и факультетом. Обработка заявок — #8; в #11 остаются HTTPS reverse proxy, резервное копирование и проверка доступа из России.
Production: `DJANGO_SETTINGS_MODULE=config.settings.production`, длинный случайный DJANGO_SECRET_KEY, hosts, пароль БД, HTTPS CSRF origins. Запустить `check --deploy`, миграции и collectstatic отдельным шагом выпуска.
Gunicorn доступен только доверенному reverse proxy, который перезаписывает X-Forwarded-Proto. Не выставлять порт БД наружу.

## Воспроизводимые зависимости

`frontend/package-lock.json` закрепляет npm-дерево; установка — `npm ci`. `backend/constraints.txt` фиксирует Python-зависимости (включая транзитивные и тестовые), применяется из requirements.txt. Обновлять их отдельным PR и повторять CI. Не менять lock-файл вручную.

Override `minimatch: 11.0.1` закрывает GHSA-g3hv-75wg-m249 в цепочке ESLint/typescript-eslint. Совместимость проверяется линтером и тестами; убрать override после исправления диапазонов upstream и чистого npm audit.

CI выполняет серверные тесты авторизации/изоляции на PostgreSQL, 3 frontend unit-теста и сценарии входа/профиля/выхода и двух независимых студентов на desktop, 360 px и WebKit/iPhone. Скриншоты сохраняются в артефакте. Это не заменяет будущую приёмку на реальных Android/iOS устройствах в #12.

Для локальных браузерных тестов нужна отдельная одноразовая БД с вымышленными данными; seed_browser.py предназначен только для такого окружения. Не запускайте seed на рабочей БД.

При подготовке основы локальная сеть не позволяла скачать пакеты; полная проверка выполнена в GitHub Actions. Для запуска у разработчика нужны установленные зависимости и PostgreSQL.

## Проверка с iPhone по Wi-Fi

Mac и iPhone должны быть в одной локальной сети. В `.env` добавьте LAN-IP Mac в `DJANGO_ALLOWED_HOSTS` (например, `localhost,127.0.0.1,192.168.1.20`), затем перезапустите Django с переменными из `.env` согласно инструкции выше. Backend оставьте на 127.0.0.1:8000: телефон обращается к нему через Vite.

В frontend запустите `npm run dev:lan`. На iPhone откройте `http://<LAN-IP-Mac>:5173`. `localhost` и `127.0.0.1` на телефоне означают сам телефон. При смене IP обновите `.env`. Не устанавливайте `ALLOWED_HOSTS=*` и не отключайте CSRF. Если сеть изолирует Wi-Fi-клиенты или firewall запрещает Node, соединение нужно разрешить в настройках локальной сети.

CI проверяет WebKit с устройством iPhone и альтернативным адресом 127.0.0.2: это покрывает маршрутизацию, Host, cookies и CSRF при входе/выходе, но не заменяет проверку конкретного физического телефона.

## Создание локального демонстрационного студента

После загрузки переменных `.env`, из backend с активной venv:

```sh
python manage.py create_demo_student six_seven
```

Команда дважды запросит пароль без отображения. Она создаёт вымышленный профиль и обычного пользователя без прав администратора. Существующие учётные записи не перезаписывает. Пароль не передавайте аргументом командной строки, не записывайте в Git и LEARNING.md.

## Обновление авторизации — #5

После переключения на ветку с этой задачей обновить зависимости и применить миграции (включая миграции axes):

```sh
pip install -r backend/requirements-dev.txt
python backend/manage.py migrate
```

Используйте окружение из `.env`, как при первом запуске. Нельзя запускать новый сервер со старой схемой БД. Существующие пользователи и их пароли сохраняются; StaffProfile — новая таблица, а роли не выдаются существующим аккаунтам автоматически.

Чтобы вручную проверить двух вымышленных студентов с разными данными, из backend с активной venv:

```sh
python manage.py create_demo_student demo_student_a --full-name "Вымышленный студент А" --group ДЕМО-А
python manage.py create_demo_student demo_student_b --full-name "Вымышленный студент Б" --group ДЕМО-Б
```

Пароли вводятся скрыто, а не сохраняются в исходниках или shell-аргументах. Существующие usernames не перезаписываются. Имена групп этой команды предназначены для демонстрационного факультета; существующую группу другого факультета команда не переназначает.

Сотрудник: создать обычного пользователя (без is_staff/is_superuser), затем superuser назначает ему StaffProfile и конкретный Faculty. Такой сотрудник входит через /auth/login/ и получает свою область в /api/v1/me/, но не административные полномочия. Если человек одновременно учится, роли назначаются явно и доступ к личным/служебным данным остаётся раздельным. Описание DTO и функций ограничения queryset — contracts/API.md.

Для проверки на PostgreSQL используйте отдельную тестовую БД/контейнер; не создавайте демонстрационные данные в чужом рабочем окружении. В CI seed_browser.py создаёт два разных профиля и сотрудника только в одноразовой БД.
